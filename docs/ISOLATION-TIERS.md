# 隔离设计：按执行点分层 + 两档运行时

> 2026-09-17（第二版）。第一版按「改起来便不便宜」排 —— 那是**错的坐标轴**：便宜和贵不是安全属性，
> **谁施加、租户能不能绕过**才是。这一版按**执行点**分四层，每层写清「项 / 谁施加 / 租户能否绕过 /
> 怎么验 / 失败模式」，然后把补齐顺序和两档运行时挂上去。
> 起点是 [ISOLATION-POSITIONING](ISOLATION-POSITIONING.md) 的自评：现行方案不是天花板。
> 决策记在 [D38](DECISIONS.md)。**本文只是设计，没动代码。**

## 〇、一条原则

**能当边界的，必须是工作负载够不到的机制施加的。**

容器里的东西分两种：

- **由容器外的机制施加到容器内进程上的**（镜像构建时烘进去的、运行时 exec 时由 Docker/内核施加的、
  宿主上持续生效的）→ 施加点在租户的权限域之外，**算边界或纵深**。
- **住在容器可写空间里、由容器内进程执行的**（装个监控、包一层脚本、改配置、容器内那道门）
  → 租户在那里是 root，**不算边界**。

所以准确说法是：**容器内的执行体不可信，但容器内的状态可以被外部固定住。**

这条不是我推的，是权威分层就这么切的：**NIST SP 800-190** 的五层是
**镜像 / 仓库 / 编排器 / 容器运行时 / 宿主 OS** —— **没有一层是「容器内部」**；
Docker 官方那篇的标题就是《Runtime Enforcement, Not Runtime Advice》，正文一句
「提示词能影响行为，运行时能限制行为」，它给的三个边界（执行 / 工具 / 凭据）全是运行时环境的属性。

**一个 2026 年的实例**（CVE-2026-25725，GHSA-ff64-7w26-62rf，high）：某个编码 agent 的 bubblewrap
沙箱**没保护自己的配置文件** —— 因为那个文件在启动时**不存在**。沙箱里的恶意代码自己建了它、
注入 `SessionStart` 钩子，重启后以**宿主权限**执行。教训不在那个 bug，在结构：**一个沙箱的配置与状态
住在它自己约束的那段可写空间里，它就不是边界。**

## 一、四层总览

| 层 | 谁施加 | 租户能绕过吗 | 我们对它的定位 |
|---|---|---|---|
| **镜像**（构建时） | 我们 | **能** —— rootfs 可写 + 有网，`apt-get install` 就装回来了 | 缩默认面、提基线；**不是边界** |
| **运行时**（容器外，exec 时） | Docker / 内核 | 不能 | **边界本体** |
| **宿主**（容器外，持续） | 宿主侧 | 不能 | **边界本体** |
| ~~容器内~~ | 容器内的进程 | **能**（主人就是 root） | **不写进安全论证**（见 §五） |

## 二、镜像层（构建时）

**已做**：去掉 `bwrap` 的 setuid 位（`chmod u-s`）；构建期自检（`dsh --version`、`require('node-pty')`）。

**要补**：

| 项 | 做什么 | 为什么值得 |
|---|---|---|
| 去掉基座自带的 setuid 位 | 实测镜像里有 **9 个**：`su` / `passwd` / `mount` / `umount` / `chsh` / `chfn` / `newgrp` / `gpasswd`，外加不在 `/usr/bin` 下、最容易数漏的 `/usr/lib/openssh/ssh-keysign`（Debian 基座自带，与 dsh 无关） | 零成本缩小默认面 |
| base 按 digest 固定 | `node:24-trixie@sha256:…`（现在是跟 tag） | 供应链：构建可复现，镜像内容不被上游悄悄换掉 |
| SBOM | 构建时产出（CycloneDX / SPDX），跟版本一起发 | 出 CVE 时能回答"我这些版本里有没有" |
| 重建 SLA | 定「critical 出来多久出重建版本」（清单里的通行值是 48 小时） | 没有节奏 = 有洞也不修 |
| 签名 / provenance | cosign + SLSA（可选） | 自托管平台收益小 —— 镜像只从自己的 GHCR 来；**先不做，写下来** |

**必须如实写下的约束：agent 的本职是装包 → 我们离不开 shell 与包管理器 → 主流清单里的「最小化基础镜像
（distroless / 去掉 shell 和包管理器）在我们这里不适用。** 那份收益（相对 `debian:12` 少一个数量级的
扫描发现）我们拿不到，原因是产品形态，不是疏漏。

**估值纪律**：镜像层的验收**不写「挡住了」，只写「默认面上没有它」**。举一个能说明问题的例子 ——
镜像里去掉那 8 个 setuid 位，租户照样能 `chmod u+s` 给自己装的二进制；真正挡住这条路的是运行时的
`no-new-privileges`。**镜像层永远只是让默认面上干净，不构成边界。**

## 三、运行时层（容器外，exec 时施加）

| 项 | 现状 | 要做什么 | 验法 | 失败模式 |
|---|---|---|---|---|
| `no-new-privileges` | **已做**（2026-09-17） | —— | 已有用例钉住整份 `SecurityOpt` | —— |
| **CapDrop** | 未做（用 Docker 默认 14 条） | `CapDrop: ["ALL"]` + 按需 `CapAdd` | **先量**：启动 → `npm install` → `git clone` → 快照，看哪一步 `EPERM` | 漏一条 = **运行期随机失败**；入口脚本实测没有 `chown` / `su`，所以"全丢"可能成立，但必须量 |
| ~~seccomp 收紧~~ | **决定不做** | ——（继续用 Docker 默认 profile） | —— | 见下 |
| `ReadonlyPaths` | 未做（Docker 默认 5 条生效） | 显式写死那 5 条：`/proc/bus`、`/proc/fs`、`/proc/irq`、`/proc/sys`、`/proc/sysrq-trigger` | 用例守着 | **设了就是整份替换** —— 抄漏一条就是静默放行（MaskedPaths 已经踩过） |
| `MaskedPaths` | 已做 | —— | 已有用例 | —— |
| 非 root 负载 + 存储属主迁移 | **已做**（2026-09-17，[D39](DECISIONS.md)） | —— | 新建与存量实例都能读写 `/data` | 存量 `/data` 里全是 root 的旧文件 → 起容器前迁；判据是**目录的实际属主**（回滚会把旧数据盖回来，记状态的做法在这里会骗人） |
| userns-remap | 未做 | 与上面那项**不一起做**：它是 daemon 级配置，一开宿主上所有容器一起变，收益与代价要单独算一轮（[D39](DECISIONS.md) 的备选②） | —— | —— |
| cgroup 限额（mem / cpu / pids） | 已做 | —— | —— | —— |
| 只读挂载 | 部分（lxcfs 三个文件 `:ro`） | 按需 | —— | rootfs 可写是产品决定（D12），不动 |

**`no-new-privileges` 落地的形态**：驱动里一个常量（跟 `MASKED_PATHS` 同一个路子，不拓宽驱动接口），
`HostConfig.SecurityOpt = ['no-new-privileges']`。**值就是这个裸字符串**，不带 `:true` 后缀 —— 两种写法
Docker 都认，但仓库里只留一种，别"顺手补全"。它**不改 uid**：容器内 setuid 位与文件能力不再提权，
进程仍以 root 跑。与下面的 `CapDrop` 互不依赖，所以它可以先单独上。

**为什么 seccomp 收紧只能算纵深**：它是**按名字与语法匹配**的执法 —— 换个二进制名、换条库调用、
用符号链接就绕开了。「没有任何黑名单能预见还没发生的行为」（这条批评出自一篇商业厂商的文章，
立场要打折，但它指出的机制是真的）。同理适用于 AppArmor 这一类。

**所以 seccomp 决定不做**（2026-09-17）。技术上还有一条更硬的理由：`SecurityOpt: seccomp=<profile>`
是**整份替换**，没有"默认 + 额外 deny"的写法 —— 收紧就得在仓库里维护一份默认 profile 的分叉，
而它会随引擎版本漂移（遮蔽表在 11 条与 12 条之间横跳已经演示过一次）。收益让给了"零漂移、零维护"。
默认 profile 继续生效，它已经挡了 `unshare(CLONE_NEWUSER)` 这一批；**也不必为了保住 bwrap 去放宽它** ——
Linux 上沙箱链靠的是第二档 Landlock，第一档本来就不可用（见 §八 #1）。

| 项 | 现状 | 要做什么 |
|---|---|---|
| 每实例一个网络 + 桥端口只发布到宿主回环 | **已做**（[D37](DECISIONS.md)） | —— |
| XFS project quota（字节 + inode 双限） | **已做**（[D18](DECISIONS.md)） | —— |

| **egress 过滤** | **空白** | 按**域名白名单**做（nftables 拦 DNS + 只放行已解析地址）。**挂点现成**：D37 每实例一个 bridge，规则按桥写，不用按 IP 追。**先定产品语义** —— 白名单会打断"agent 装任何包"这个本职能力 |
| **运行时检测** | **空白** | 宿主侧 eBPF 做**行为**检测（Falco / Tetragon 一类）；NIST 自己举的例子就是"容器里起了它在构建时没有的 shell" —— 正是我们的威胁模型。要有**告警去处**，否则只是装了软件 |
| **运行时与内核的补丁节奏** | **空白** | 共享内核 ⇒ **内核与 dockerd / runc / containerd 的版本本身就是攻击面**（CVE-2024-21626 是 runc 的：扫镜像层永远看不到跑在它下面的 daemon 里的洞）。要定"关键 CVE 出来多久升"并演练一次。**这一条可能比换档位更值钱**：一份 2026 年的沙箱对比研究把"产品的 pin 策略"列为运营侧的主导变量 —— 引擎侧打补丁约 **0 天**，而**下游滞后从 0 天到 471+ 天**都有 |
| **信任等级混布** | 已存在、未写下 | 控制面（可信）与实例（不可信）**同一宿主**，且控制面握着 docker.sock —— NIST 把这列为编排器风险。写进残余风险，不能只写隔离 |

## 五、不写进安全论证的那一类（列出来，防止以后有人往里加）

| 东西 | 为什么不算 |
|---|---|
| dsh 自己的沙箱链（bwrap / Landlock） | 它是**产品功能**（给用户自己用的），配置与状态住在容器里 → 与 CVE-2026-25725 同一类结构。**我们的边界不含它** —— 这也说明 gVisor 那条"沙箱链全灭"是**功能**问题，不是安全取舍 |
| 实例内 Caddy 那道门（门③） | 有效**障碍**，但配置在容器里、主人能改。它挡的是"别人进这个实例"，而能关掉它的只有实例主人（**自伤，不是给别人开路**）→ 有效，但不是我们能依赖的边界 |
| 任何容器内的监控 / 容器日志 | 租户能伪造、能抹。可用的检测信号只有宿主侧产出的 |

**这一列存在的意义**：以后回头改设计时，不许把其中任何一条写进"所以我们安全了"的论证里。

## 六、两档运行时

| | **T1 加固 Docker**（默认档） | **T2 强隔离**（可选档，宿主支持才提供） |
|---|---|---|
| 隔离边界 | 共享内核 —— 逃逸即宿主失陷 | 每实例一个**真内核** —— 逃逸要先破 hypervisor |
| 谁用得上 | 任何有 Docker 的宿主 | 有 KVM / 嵌套虚拟化的宿主 |
| 前提 | 无 | `/dev/kvm` |

**T2 不是「以后替换 T1」，是并存的一档**（driver 接缝 `runtime/driver.ts` 本来就是给这个形状留的）。
补一句这轮想清楚的，以及一条**要打折的期待**：

- T2 能解掉两件：**逃逸直达宿主内核**、**宿主全局 `/proc` 与 DMI**（真内核 = 自己的视图）。
- **T2 解不掉侧信道**。2026 年那篇跨容器**与跨 VM** 的 page-cache 计时侧信道研究覆盖了 Docker /
  gVisor / Kata（QEMU、Cloud Hypervisor、Firecracker），结论是**虚拟化改变了泄漏形态、但没有消除它**；
  只要 I/O 路径上还是共享的、宿主可缓存的文件对象（**virtio-fs 正是这一类**），信号就在。
- **由此一条设计修正**：T2 的 `/data` **不要走 virtiofs / 9p，要走块设备** —— 那篇的实测结论是
  "直接 I/O 与专用块设备能显著衰减甚至消除信号"。顺带和 D2 已有的性能理由（dsh 的小文件 I/O
  正打中 virtiofs 弱项）同向：**这一条是安全与性能同时指向同一个选择**。

T2 的面矩阵（要满足同样的四条边界 + 配额 + 门）：

| 面 | T1 现在 | T2 要解决什么 |
|---|---|---|
| 网络 | 每实例一个 bridge + 回环发布 | 每个 microVM 要自己的网络命名空间；发布形态要重做 |
| 存储 | 池目录 bind 进容器 | 池目录进 guest —— **用块设备，不用 virtiofs / 9p**（侧信道理由见上）。**配额不用重做** —— project quota 在宿主文件系统上 |
| 资源 | cgroup（mem / cpu / pids） | CPU / 内存变成 vcpu / mem；pids 要 guest 内做或放弃 |
| 门 | 容器内 Caddy 校验 header | **不变** |
| 镜像 | OCI 镜像 + 卷 | 要 guest kernel / rootfs，分发形态不同 |
| dsh 沙箱链 | bwrap 死、Landlock 活 | guest 是真内核，两档**都可能**活 —— 但按仓库规矩**换运行时必须重验，不能继承** |

实现路线：**Kata Containers 经 containerd**（[D2](DECISIONS.md) 的升级路径；裸 Firecracker 的运维成本更高）。
探测方式建议**安装器在宿主探完落一个能力标记**（与 [D35](DECISIONS.md) 的存储池同一形状），
而不是把 `/dev/kvm` 挂进控制面。**什么时候做**：等第一个真有 KVM 的宿主出现 —— 现在只需保证不挡路。

## 七、补齐顺序与验收

| # | 做什么 | 层 | 存量要重建 | 验收 |
|---|---|---|---|---|
| 1 | 去掉基座 9 个 setuid 位 + base 固定 digest | 镜像 | 是（换镜像才生效） | 镜像里 `find / -perm -4000` 为空；实例照常起、`npm install` 照常 |
| 2 | 量 dsh 的最小 capability 集 | 运行时 | 否 | 可复现的命令 + 输出 |
| 3 | `no-new-privileges`（**已做**，2026-09-17）+ `ReadonlyPaths` 显式写死 | 运行时 | 是 | 真实流程照常；用例守住 ReadonlyPaths |
| 4 | CapDrop（按第 2 步的清单） | 运行时 | 是 | 同上 + 一条"被丢的能力真的丢了"的用例 |
| 5 | ~~seccomp 收紧~~ **决定不做**（理由见 §三） | —— | —— | —— |
| 6 | 非 root 负载 + 存储属主迁移（**代码已落定**，2026-09-17，[D39](DECISIONS.md)） | 运行时 + 宿主 | 是，**且要迁属主** | 新旧实例都能读写 `/data`；迁移可回退 |
| 7 | egress 白名单（先定产品语义） | 宿主 | 否 | 白名单内可达、外不可达；装包流程按定义仍可用 |
| 8 | 运行时检测（宿主侧、行为型） | 宿主 | 否 | **有告警去处**才算完成 |
| 9 | 补丁节奏：内核 / dockerd / runc / containerd | 宿主 | 否 | 写下节奏并**演练一次**升级 |
| 10 | SBOM + 镜像重建 SLA | 镜像 | 否 | 每个版本带 SBOM；critical 的响应时间写进流程 |
| 11 | T2 强隔离档 | 运行时（新 driver） | —— | 有 KVM 宿主才开工；开工前先重验沙箱链 |

**共同的成功判据**：加固类改动的典型事故是**静默坏** —— 容器起得来、agent 跑一会儿才 `EPERM`。
所以每一步都要跑一遍**真实流程**（起实例 → 装包 → 跑命令 → 快照），不能只看"容器起来了"。

## 八、待测量（写下来的未知项，别当已知）

1. ~~真机上 `unshare -U` 为什么 `EPERM`~~ —— **2026-09-17 已定案，移出本表**。原因不是宿主收紧：
   是**两层叠加** —— Docker 默认 seccomp profile 挡 `unshare(CLONE_NEWUSER)`；放开后 bwrap 仍死在
   `mount(2)`，第二层是宿主 AppArmor 的 `docker-default` profile（整条 `deny mount`）。宿主 sysctl
   从头到尾没限制。原先那个「宿主主动收紧未特权 userns、救 bwrap 等于拆掉宿主一层加固」的假设
   **不成立**（详见 D38 的 2026-09-17 实测注记）。
   **连带的决定**：Linux 上沙箱链靠的是第二档 Landlock（ABI 6），所以**不必为保住 bwrap 去放宽
   seccomp 或 AppArmor 任何一层**。
2. **dsh 全流程的最小 capability 集**（第 4 步）。
3. **去掉那 9 个 setuid 位会不会影响 dsh / apt 的正常工作**（第 1 步，可以立刻量）。
   ⚠️ 实测镜像是 **9 个**（多一个不在 `/usr/bin` 下的 `/usr/lib/openssh/ssh-keysign`），数清单时别漏。
4. **egress 白名单对"装包"的实际影响** —— 需要放行哪些域名（第 7 步）。
5. **T2 下 dsh 沙箱链两档是否可用**（guest 内核有没有 Landlock / userns）—— 开工前必测。
6. **迁属主在真机上的耗时**（第 6 步）：`/data` 是一次全目录遍历。参考点是同一条路上的快照
   （`setImage` 本来就要 `cp -a` 整份 `/data`），量出来若不可接受，退路是「只改顶层 + 顺带校验」。

> ~~dsh 全流程的 syscall 面~~ 已随「seccomp 决定不做」作废（2026-09-17）：没有要收紧的 profile，
> 也就没有要量出来喂给它的 syscall 清单。

## 九、明确不做

- **不用 gVisor**：实测两档沙箱全灭，dsh 会**拒绝执行任何命令** —— 不是慢，是不能跑。
- **不做裸 Firecracker**：运维成本高于经 containerd 间接使用。
- **不开 `--privileged`、不关 `no-new-privileges`**。
- **T2 的 `/data` 不用宿主目录直挂** —— 走块设备（理由见 §六）。⚠️ **这一条只对 T2 成立**：
  T1 在 Linux 上**就是**宿主目录直挂（`<pool>/<key>` bind 进 `/data`，见 [ARCHITECTURE §四](ARCHITECTURE.md)），
  XFS project quota 正依赖那个宿主目录；开发机（Docker Desktop）上 T1 退回命名卷，理由与本节无关
  （VM 共享文件系统的硬链接语义问题，见 `renderers/instance.ts` 的注释）。别把这条读成对 T1 的限制。
- **不把容器内的控制写进安全论证**（见 §五）。

## 十、证据说明

这一版引的东西分三档，看的时候分清：

- **一手实测**（最可信）：9 个 setuid 位、开发机上 `unshare -U` 的行为、lxcfs 八文件表、
