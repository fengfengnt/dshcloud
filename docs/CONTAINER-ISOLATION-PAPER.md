# 容器作为不可信代码执行环境：隔离、加固与信息隐藏的实测研究

## 摘要

把一个容器当作"不可信代码的边界"，是当今多租户平台最常见的选择。但这个选择实际提供了什么、
又漏掉了什么，往往停留在参数清单的层面——清单能告诉你应该设置哪些开关，却回答不了两个更要紧的问题：
这些开关各自挡住了哪一类对手，以及**有没有哪一类泄漏根本不在清单的视野里**。

本文在一个真实运行的多租户平台上，对容器边界做了逐项实测，并按"施加点是否位于工作负载的权限域之内"
把结论重组成三层：**隔离**（谁够得着谁）、**加固**（容器能做什么）、**信息隐藏**（容器能读出宿主的什么）。
实测在两类宿主上完成——一台普通 Linux 服务器（Debian 13、4 核、8 GiB 内存、无 KVM）与一台
Docker Desktop（linuxkit 内核）开发机，覆盖网络分段、文件系统配额、运行时边界、四类加固参数与
八项信息泄漏面。我们同时对照了 NIST SP 800-190、CIS 基准一类的行业清单与相关学术文献。

三条结论。第一，**三层里只有前两层在主流清单的视野内**：隔离与加固都有成熟的条目，而"信息隐藏"
——容器通过 `/proc`、`/sys` 读出宿主内存总量、开机时刻、CPU 型号，进而指纹宿主或推断邻居负载
——几乎没有任何清单覆盖，学术上也没有对应的成熟领域。第二，**加固的效力被系统性高估**：
不能把 seccomp、AppArmor 与基于进程名的检测混为一谈：seccomp 在内核检查系统调用，二进制改名不能绕过；
AppArmor 的效果取决于策略覆盖、附着和转换规则。它们是宿主施加的强制控制，但不消除共享内核风险；
一份 2026 年的对比研究进一步显示，运营侧的重要变量是"补丁节奏"
而非隔离技术选型——引擎侧补丁约 0 天，而下游滞后从 0 天到 471 天以上都有。第三，**在共享内核的前提下，
信息隐藏存在结构性上限**：应用最广的用户态方案（FUSE 覆盖 `/proc`）只能篡改文件读取路径，
一个直接调用 `sysinfo(2)` 的程序即可绕过；真正能覆盖它的机制（时间命名空间）在内核中已经存在，
却因容器运行时不暴露偏移量而无法使用。

我们也报告了一个反直觉的结果：被广泛推荐作为强隔离手段的两个运行时中，用户态内核方案在本负载上
**无法运行**（应用自身的进程沙箱链在其下两档全灭，按失败即拒绝的语义，任何命令都不会被执行），
而硬件虚拟化方案要求宿主支持嵌套虚拟化——多数廉价虚拟服务器并不提供。

## 1 引言

容器共享宿主内核。这句话的后果比它读起来更重：容器逃逸意味着**宿主失陷**，而不只是"串到邻居"。
对运行不可信代码的平台而言，这既是最重要的边界，也是最容易被参数清单掩盖的边界。

过去两年，随着编码 agent 成为一类常见工作负载，"把 agent 关进容器"变成了一种默认答案。这个答案
在威胁模型上是否成立，取决于三个被反复混为一谈的问题：

1. **隔离**：一个被攻陷的实例能碰到谁？
2. **加固**：它能对自己所在的宿主内核界面做什么？
3. **信息隐藏**：它能**读出**关于宿主的什么？

第 3 条最少被讨论，但它有独立的现实后果：宿主的内存总量、开机时刻、CPU 型号与核数、磁盘设备名、
内核 slab 分配情况，都可以从工作区内一眼读出。这些数字本身不是数据泄漏，而是**形状泄漏**——
它们让租户能够指纹宿主，并把宿主的负载变化与重启当作跨租户侧信道。

本文的贡献有三：

- **一套按"施加点"组织的判据**（第 3 节），用来判断一个控制手段到底算不算边界。它把 NIST SP 800-190
  的五层模型（镜像 / 仓库 / 编排器 / 容器运行时 / 宿主 OS）与工程直觉对齐，并给出一条可操作的结论：
  **凡是住在工作负载可写空间里、由工作负载自己的进程执行的控制，都不构成边界**。
- **一组一手实测**（第 4–7 节）。全部数字来自同一平台、同一镜像、可复现的命令，包括网络分段的
  前后对照、文件系统配额的硬限验证、两个更强运行时的可用性与开销、四类加固参数的实际行为，
  以及八项信息泄漏面的挂载前后对比。
- **一次对照**（第 8、10 节）。把实测结论与行业清单、学术文献放在一起看，指出清单的盲区
  （信息隐藏、补丁节奏）与文献的空白（"隐藏"这一侧几乎没有对照研究）。

## 2 威胁模型与研究范围

**前提假设：实例 = 不可信代码执行环境。** 工作负载是一个编码 agent：它会执行任意 shell 命令、
安装依赖、读写文件、发起网络请求，并与外部模型服务通信。这些都是它的本职功能，不是需要被阻止的
异常行为；隔离的目标不是阻止它们，而是**把影响范围限制在单个实例内**。

这个假设并非保守估计。SANDBOXESCAPEBENCH 一类的基准把对手明确刻画为"**一个有 shell 权限、
有动机的对抗性 agent**"，覆盖配置错误、权限分配失误、内核缺陷与运行时/编排弱点四类逃逸路径，
其结论是：**只要存在漏洞，模型能够识别并利用它**[1]。因此本文不讨论"工作负载是否会去找路"，
只讨论"路是否存在"。

**在范围内**：容器运行时（本文以 Docker 为主）、宿主侧的网络与存储控制、信息泄漏面、
以及应用自身的进程沙箱在整体防御中的位置。

**不在范围内**：宿主运营者（拥有宿主或容器守护进程权限的人不受应用层限制）、镜像供应链深处的
投毒、以及物理侧信道。硬件虚拟化（microVM）只在作为**对照**出现——它是同一问题的另一档答案，
不是本文的主题。

## 3 一条判据：施加点在不在工作负载的权限域内

容器里的东西分两类：

- **由容器外的机制施加到容器内进程上的**：镜像构建时烘进去的内容、运行时在 `exec` 时由容器引擎
  与内核施加的参数（能力集、seccomp、cgroup 限额、只读挂载）、宿主上持续生效的规则（网络分段、
  文件系统配额、防火墙）。它们的施加点在租户的权限域之外，**算边界或纵深**。
- **住在容器可写空间里、由容器内进程执行的**：装个监控代理、包一层脚本、改一份配置文件、
  容器内部的那道校验。租户在这些位置是 root，**不算边界**。

一句话概括：**容器内的执行体不可信，但容器内的状态可以被外部固定住。**

这条判据与权威分层一致。NIST SP 800-190 把容器安全风险分为**镜像、仓库、编排器、容器运行时、
宿主 OS** 五层[2]——**没有一层是"容器内部"**。容器厂商的公开表述走得更直白：
"提示词能影响行为，运行时能限制行为"，隔离的落点永远是运行时环境，而不是被约束的工作负载本身[3]。

**一个 2026 年的实例**说明了这条判据的现实分量。CVE-2026-25725（严重级别 high）中，某个编码
agent 的进程沙箱**没有保护自己的配置文件**——原因仅仅是该文件在沙箱启动时**不存在**。沙箱内的代码
自行创建了这个文件、向其中注入启动钩子，于是这些钩子在下次启动时**以宿主权限**执行[4]。这里出错的
不是沙箱实现，而是结构：**一个沙箱的配置与状态，住在它自己约束的那段可写空间里**。

由此得到本文后续反复使用的一个结论：**应用自带的进程沙箱不构成平台的安全边界**。它是产品功能——
用来降低用户自己误操作的风险——但在安全论证中不能计入。第 5.4 节关于运行时选择的实测，
也因此只影响"功能是否可用"，不影响"边界是否成立"。

## 4 方法与实验环境

**环境。** 主实验在一台普通 Linux 服务器上完成（Debian 13、4 核、8 GiB 内存、无 KVM，
本身是虚拟机的客户机且宿主未开启嵌套虚拟化）；对照实验在 Docker Desktop（linuxkit 内核 6.10.14）
上进行；另有一组文件系统配额的实测在第二台 Linux 宿主上完成（Debian 12 / 内核 6.1 / 容器引擎 29），
文中逐处标注。三者都是常见的部署环境，差异本身构成本文的一部分结论。

**方法。** 三项纪律贯穿全部实测：

1. **对照测量**。信息泄漏面采用"同一容器内挂载前后各读一次"的方式；网络隔离采用"分段前后各测一次"。
2. **真实流程**。涉及加固参数的判断，不以"容器能否启动"为准，而以完整流程为准：启动实例、
   安装依赖、克隆仓库、生成快照。原因是加固类配置的典型故障是**静默失败**——容器照常起来，
   agent 跑到中途才因权限不足失败。
3. **不继承结论**。更换运行时或宿主后，既有结论一律重测。这条规矩来自一次直接的教训：
   文献与文档中关于"某运行时支持某机制"的说法，在真实环境中多次不成立。

**证据分级。** 本文对每个论断标注来源等级：**一手实测**（可复现的命令与输出）、
**标准与官方文档**、**学术论文**、**厂商或二手材料**（后者一律注明并打折）。

## 5 隔离：边界在哪

### 5.1 网络：默认桥是一份反面教材

在实例各自接入默认桥的时期，所有实例共享一个 L2 广播域。实测（2026-09-15）：在实例内对
`172.17.0.0/16` 做 ARP 扫描，邻居容器的 `:8080` 端口**直接有响应**。这意味着三件事同时成立——
直连邻居端口、扫描邻居端口、ARP 欺骗；而这条路径上转发的是**明文**（TLS 在入口处终止），
唯一的一道校验（容器内的头部校验）所依赖的令牌正是明文过桥的。

改为**每实例一个独立网络**之后，三条路径同时消失：跨网段不可达，实例内的邻居表里连条目都没有。

分段之外，桥端口**只发布到宿主回环**，不对局域网暴露。这两半互不替代：分段管实例之间，
回环发布管局域网与宿主。

残余的三条路径同样有实测记录：

- **容器够得到宿主上绑定非回环地址的服务**。容器访问宿主走的是宿主 INPUT 路径：实测（2026-09-12）
  绑定 `0.0.0.0` 的服务可达，绑定 `127.0.0.1` 的不可达。也就是说宿主的 SSH、任何 `0.0.0.0`
  监听都在实例的射程内。容器引擎不提供原生开关（"隔离网关"模式必须同时关闭出网，而实例需要出网
  安装依赖），只能由宿主侧防火墙规则处理。
- **出网不受限**。容器引擎不提供出网过滤，本文所对照的几份主流加固清单也未把这一项列入——
  它们默认更上层的编排系统已经提供了网络策略。
- **开发机上的回环发布不是边界**。Docker Desktop 提供的"宿主别名"是指向宿主 localhost 的代理，
  于是宿主回环上的**所有**监听（包括其他实例发布的端口）对所有容器开放（2026-09-15 实测）。
  这是开发机特有的：在 Linux 宿主上，容器到宿主回环的连接实测全部被拒。

最后是一条容易被忽略的失效模式：宿主同时运行 firewalld 与容器引擎时，firewalld 的一次重载会
冲掉引擎写入的跨网络规则，且引擎不会重建它们（CVE-2025-54410，影响特定版本区间）。此时
**隔离静默失效而配置看起来完全正确**——这比没有配置更危险。

### 5.2 存储：配额必须落在文件系统的分配路径上

容器的可写层与挂载卷是两回事：容器引擎提供的"卷大小"选项只约束前者，对挂载进去的目录无效；
命名卷与宿主目录则完全没有配额。真正能给出硬上限的只有文件系统本身——本文采用 XFS 的 project quota，
按实例分配一个 project ID，同时限制**字节数与 inode 数**。

实测（2026-09-12，Debian 12 / 内核 6.1 / 容器引擎 29，loopback XFS 池）：

| 项 | 结果 |
|---|---|
| 限 256 MiB、写入 400 MiB | 停在 256.0 MiB，返回 `ENOSPC` |
| 实例目录的容量视图 | 报的是**配额**（256.0 MiB），不是宿主盘（池子 4032 MiB） |
| inode 配额 | 与字节配额同一机制，超限的创建同样被拒 |
| pool 创建 / 实例目录创建 | 79 ms / 约 7 ms |

三点工程教训值得单独列出：

1. **字节与 inode 必须同时限制**。只限字节时，数百万个零字节文件即可耗尽宿主 inode，
   使整台机器的文件系统瘫痪——这不需要漏洞，也不需要技巧。
2. **配额设置的失败是静默的**。读取用量不需要特权，写入限额需要；缺少特权时限额不会生效，
   而它**不会报错**。因此启动时必须真正设置一次限额并读回校验，校验失败即拒绝启动。
3. **开发机通常做不到**。Docker Desktop 的 linuxkit 内核裁掉了配额支持，挂载选项一律返回
   `EINVAL`。那里只能退回无配额的命名卷，界面上的配额必须显示为"无上限"——静默的配置失败
   比显式的报错更糟。

### 5.3 凭据：实例内零跨实例凭据

实例容器内不注入数据库凭据、平台密钥、容器守护进程套接字，也不共享任一台全局的签名密钥。
跨实例的认证令牌按实例独立派生。实例之间真正共享的东西只剩一个：内核。

### 5.4 内核：逃逸的含义，与两个更强运行时的实测

共享内核意味着容器逃逸直接等于宿主失陷。业界的应对是按**信任等级**分档：可信负载用标准容器，
中等信任用用户态内核，不可信负载用硬件虚拟化。本文对后两档在同一台真机、同一镜像上做了实测。

| | 进程沙箱链 | 结论 |
|---|---|---|
| 标准运行时 | 链的候选档中，**第二档可用**（Landlock ABI 6），第一档（bubblewrap）因创建命名空间被拒而不可用 | 链成立，命令可执行 |
| 用户态内核（gVisor） | 第一档同样被拒；第二档**未实现**（`ENOSYS`） | **两档全灭**——按"失败即拒绝执行"的语义，**任何命令都不会被执行** |

也就是说，用户态内核方案对本负载不是一个"更慢"的选项，而是一个**不能运行**的选项；
其代价也无法通过调优弥补。性能对照（同一台机器，单位为毫秒）显示，若它可用，开销本在可接受范围：
冷启动 426 / 430，安装一个网络依赖 2146–2324 / 3191–3413（约 1.45 倍），写入 2000 个小文件
172 / 189；但在"解包约 850 个小文件"这类负载上放大到 32 / 176（5.5 倍）——而这正是编码 agent
的日常形态。后续在负载机器上复测（同一台机器上已有多个实例在线）得到安装依赖 1.8–2.4 倍、
从启动到入口响应 12.9 s / 20.5 s，量级一致。

硬件虚拟化档则被硬件挡住：目标宿主是虚拟机客户机，未开启嵌套虚拟化，`/dev/kvm` 不存在。
这不是软件选择问题——多数廉价虚拟服务器不提供该能力。

**两条实测给出的结论不同层次**：标准运行时之所以成立，靠的是**第二条**候选档（内核的
Landlock 机制），而非应用沙箱链中更常被提及的第一档。这一点直接影响了后文的加固方案设计。

## 6 加固：效力与边界

### 6.1 清单挡什么

主流加固清单（容器厂商安全文档、云厂商指南、CIS 基准一类的条目划分）高度一致：禁止特权模式、
按需丢弃能力、禁止新提权、seccomp 配置文件、遮蔽与只读路径、资源上限、最小挂载面。这些条目的
威胁模型是"别让容器读到宿主的敏感文件、别让它拿到多余权限、别让它耗尽资源"。

清单的有效性有实证支撑：一项互联网规模的测量研究（2024）发现了 **1,003,947 个配置错误且暴露
在公网的容器组件**，多数运行默认配置与过期版本，其中一部分可导致敏感信息泄漏或远程代码执行，
且出现在知名机构、政府与企业中[5]。**默认配置在生产环境中就是被攻击的那一批。**

### 6.2 两个清单不写、实测才会暴露的坑

**其一，遮蔽路径是"整份替换"而非"追加"。** 容器引擎的默认遮蔽列表不会出现在容器的配置里，
一旦你显式设置该项，默认列表即被整体替换。更麻烦的是默认列表本身**随引擎版本漂移**：
本文在同期两台机器上取到的默认列表长度为 11 与 12，差异是 `/proc/interrupts`。可靠的写法是
**照抄一份并写死**，同时用测试守住。本文平台照此办了——驱动里写死一份 **13 条**的清单
（引擎默认那 12 条 + 本平台加的 `/sys/devices/virtual/dmi`），并有用例钉住。

**其二，"设了"不等于"生效"。** 本文平台的实例规格中早有进程数上限字段，界面上可以调整，
但驱动从未把它传给运行时——**改了不生效**，直到一次专门排查才发现。这一条对所有资源类参数都成立：
必须有一条断言"参数确实被传下去了"的用例。（写进本文时该缺陷已修：驱动确实把 pids 上限传下去了，
真机在跑的实例上是 `PidsLimit=512`。）

### 6.3 区分内核强制控制与行为检测

seccomp 过滤系统调用编号及可检查的参数，不依赖程序名；改名、替换库或直接发起系统调用不能绕过
对该系统调用的拒绝。AppArmor 在内核执行强制访问控制，其覆盖取决于具体策略及进程的策略转换。
按命令字符串或进程名匹配的检测可能存在语法绕过，但不能把该结论推广到 seccomp 或所有 LSM 策略[6]。

一个公开的例子足以说明其脆弱性。为了限制未特权用户命名空间的创建，某发行版采用基于
强制性访问控制策略的方案，结果被公布出**三个绕过**：切换到已配置且允许该权限的既有策略、
使用默认安装中唯一允许该权限的程序（busybox）、以及通过 `LD_PRELOAD` 借一个允许该权限的
桌面程序建立会话[7]。

该案例证明特定发行版策略存在绕过，不能证明 seccomp 可通过改名绕过。seccomp 和 LSM 是隔离边界中的
内核强制控制，也承担纵深防御作用。sysctl 同样需要核对内核支持和业务兼容性；关闭 userns 会影响 dsh 使用的沙箱。

### 6.4 补丁节奏是运营侧的主导变量

一份 2026 年发布的沙箱对比研究[8]比较了五款面向 AI 沙箱的产品、三类架构（硬件虚拟化 / 用户态内核 /
标准容器），在六个轴上测量：宿主攻击面、信息泄漏、纵深可叠加性、公开 CVE 史、补丁节奏、上游
模糊测试投入。两个结论对工程决策有直接影响：

- **属性按"架构类"分层，而不按"产品"分层**——选择哪一类架构决定了大部分性质；
- **产品的版本固定策略是运营侧的主导变量**：引擎侧打补丁的中位时间约为 **0 天**，
  而下游产品的滞后分布在 **0 天到 471 天以上、不透明、乃至无限**之间。

对本负载而言，这条结论把"内核与容器引擎的版本节奏"从一条运维杂项提升为高杠杆项：在共享内核的
前提下，内核与守护进程本身就是攻击面，扫镜像层永远看不到跑在它下面的守护进程里的漏洞。

### 6.5 加固清单的实测缺口

在同一平台上逐项核对后发现，标准清单里有四项未做：能力集丢弃、禁止新提权、seccomp 收紧、
只读路径显式设置。此外，工作负载以 root 身份运行，容器内没有降权环节——而这四项与降权之间存在
依赖关系：在负载以 root 运行、且数据目录属主为 root 的前提下，丢弃能力（尤其是
`DAC_OVERRIDE`、`CHOWN`）需要先解决存储目录的属主方案，否则会以"运行期随机失败"的形式暴露。

这也解释了为什么第 4 节强调"真实流程"验收集：这类改动的失败模式是静默的。

（**写进本文后已动工**：四项里"禁止新提权"已设上——`SecurityOpt` 置 `no-new-privileges`；
seccomp 自定义收紧的历史决定是暂不做，原因是兼容性及维护成本，而非能被改名绕过；引擎的 `seccomp=<profile>` 只能整份
替换、会随版本漂移；工作负载已改为固定非 root（`1000:1000`），上面那条"降权与存储属主"的依赖关系
就是靠**平台侧在建容器前递归迁属主**解开的（[D39](DECISIONS.md)）——在容器内降权这条路走不通，
`CapDrop: ALL` 下 `su` / `setpriv` 全是 `EPERM`。剩下的能力集丢弃与只读路径显式设置待做。
落地状态以 [ISOLATION-PLAN](ISOLATION-PLAN.md) 为准。）

## 7 信息隐藏：容器能读出宿主的什么

### 7.1 问题

容器与宿主共享内核，因此 `/proc` 中有一批文件反映的是**宿主全局**的状态：内存总量、开机时长、
负载、磁盘 I/O 计数、slab 分配情况；`/proc/stat` 里的系统启动时刻同理。CPU 配额与内存上限是例外——
它们由 cgroup 提供，每容器一份。

这些数字的现实意义有两层：**指纹宿主**（几核、多大内存、哪天开的机）与**跨租户侧信道**
（推断邻居的负载变化、宿主的重启事件）。它泄漏的是形状，不是内容。

### 7.2 用户态方案的真实能力，与它的结构性上限

最常见的缓解手段是 lxcfs：一个基于 FUSE 的文件系统，按读取者所属的 cgroup 生成对应的
`/proc` 内容。本文在真机上对它的**全部八个文件**逐个做了挂载前后对照（同一容器、宿主 8 GiB /
4 核、容器限额 2 GiB 单核）：

| 文件 | 未挂载（宿主值） | 挂载后 | 结论 |
|---|---|---|---|
| `meminfo` | `MemTotal: 8138036 kB` | `2097152 kB`（= 实例限额） | **生效** |
| `uptime` | `536551` | `0.09` | **生效** |
| `swaps` | `/dev/vda2 … 780` | `none virtual … 0` | **生效** |
| `loadavg` | `0.50 0.52 0.36 1/480` | `0.50 0.52 0.36 1/481` | 不生效（负载值透传，仅进程数为容器值） |
| `stat`（`btime`） | `1788955443` | `1788955443` | 不生效 |
| `cpuinfo` | 4 核、宿主型号 | 完全相同 | 不生效（按 CPU 集伪造，与配额机制不匹配） |
| `diskstats` | 12 行 | 12 行 | 不生效 |
| `slabinfo` | 213 行 | 213 行 | 不生效 |

八个文件里只有三个真正改变了取值。**其余五个属于"提供了但无效"**——挂载它们只是增加了挂载点。

更关键的是这一类方案的结构性上限：它只篡改**文件读取路径**。实测（2026-09-16）：在挂载了上述三个
文件的同一容器内，`/proc/meminfo` 报告 2 GiB、`/proc/uptime` 报告 0.09 秒，而一个直接调用
`sysinfo(2)` 的程序（如 busybox 的 `free`，以及若干语言运行时）**照样返回宿主的 8138036 kB
与 536750 秒**。因此这类方案的准确表述是**降低可读性，而不是边界**。

值得注意的是，这条路线本身是内核维护者当年给出的方向。2012 年有人提出让 `/proc/meminfo` 按调用者
所属的内存 cgroup 报数，被内核开发者否决——理由之一是 `meminfo` 会影响**库**的行为，而不只是
应用程序，因此不能靠"改写用到它的程序"来绕过；被推荐的替代方案正是**用 FUSE 覆盖 procfs**[9]。
同样值得注意的是，该项目自身的议题区里，有托管商报告"容器内 `htop` 看到宿主活动"并称其为安全泄漏，
该议题**被关闭且没有答复**[10]——项目的定位自始至终是资源可见性。

### 7.3 被运行时挡住的内核机制

与直觉相反，`/proc/uptime` 与 `/proc/stat` 的 `btime` **在内核层面是可以伪装的**：

- **时间命名空间**（Linux 5.6 起）虚拟化 `CLOCK_MONOTONIC` 与 `CLOCK_BOOTTIME`，
  官方手册明确把 `/proc/uptime` 列入受影响范围[11]；
- 一个内核补丁让 `/proc/stat` 的 `btime` 也随时间命名空间的偏移量走[12]。

它比 FUSE 方案强的地方在于：这是**内核层的真值伪装**，因此连直接调用 `sysinfo(2)` 的程序
也一并覆盖（该调用返回的运行时同样来自被虚拟化的时钟）。

障碍在运行时一侧：容器引擎直到较新版本（29.5）才开始为容器创建时间命名空间，且维护者明确说明
**"时间命名空间只影响单调时钟"**，**没有暴露偏移量配置**[13]。换言之，机制在内核里已经就位，
而使用者拿不到开关。（本文主实验环境的引擎版本为 29.8.0：命名空间已经在建，缺的是偏移量。）

这是本文认为"隐藏"这一层最具价值的升级路径——**优先级高于继续寻找更多可伪造的文件**。

### 7.4 侧信道不止 `/proc`

即便把上述文件全部处理干净，共享硬件上的信息流动依然存在。近期研究给出的几条：

- **页缓存计时侧信道跨容器与跨虚拟机**：只要 I/O 路径上存在共享的、宿主可缓存的文件对象
  （覆盖文件系统层、virtio-fs 导出、loop 设备都属于此类），信号就存在；虚拟化改变了泄漏的形态，
  **但没有消除它**。缓解手段是直接 I/O 与专用块设备[14]。这条结论直接影响"用硬件虚拟化换取隔离"
  的预期：**换运行时能解决逃逸路径，但解决不了侧信道**。
- **共享内核锁的争用**可以量化两个工作负载之间的隔离程度，最常见的干扰源是文件系统日志与
  内核页分配器[15]。
- **内核数据结构的占用率**可以从无特权的用户态通过系统调用计时读出（KernelSnitch，NDSS '25）[16]。
- **CPU 频率遥测可以指纹工作负载**：在并发运行多个容器、分布在不同核心的条件下，区分容器镜像的
  准确率可达 **84.5%**；在云环境中，**不到 40 秒、准确率超过 70%**[17]。缓解方向是噪声注入。
  这一条与 `/proc` 毫无关系——它说明"藏干净"在共享硬件上不可能成立。

### 7.5 与上述无关的一条：平台身份

宿主是否为虚拟机、机型为何，写入 `/sys/devices/virtual/dmi/id/*`。它与上述机制无关，
可被运行时提供的**遮蔽路径**机制覆盖，且该覆盖与运行时选择无关——包括在硬件虚拟化档下同样需要。

## 8 讨论

**8.1 三层里只有两层在清单视野内。** 隔离与加固都有成熟的条目体系；信息隐藏没有。我们对照的
多份 2026 年清单类材料，遮蔽的都是"敏感文件"（内核内存转储、固件接口一类），**没有一份把
"宿主全局的数字"当作泄漏面**。学术上同样稀薄：以"反指纹""隐藏容器化环境"为目标的系统性研究
几乎找不到，中文与英文文献中都只有零星工作（例如针对 SaaS 环境做容器指纹匿名的网络欺骗方法）。
这意味着这一层没有现成的最佳实践可以照搬——**只能靠自己的实测推进**。

**8.2 加固的效力被高估的地方。** 两个具体形态：其一，按名字/语法匹配的执法容易被绕开，
却被当作主要防线；其二，把镜像层当作边界。镜像层的加固（去掉 setuid 位、最小化基础镜像、
按摘要固定版本）确实降低默认攻击面，但工作负载可写文件系统且有网络出口时，它可以把去掉的东西
装回来——例如自行给二进制加上 setuid 位，而真正阻止这条路径的是运行时的"禁止新提权"参数，
不是镜像。**镜像层让默认面干净，但不构成边界。**

**8.3 对强隔离的合理预期。** 本文的实测给出两条相互独立的边界：硬件虚拟化能挡住逃逸与
宿主全局的 `/proc`，但挡不住侧信道（7.4）；用户态内核在本负载上不能运行。因此"最强的档位"
并不是一个无条件更优的选项，而是一个有前提条件的选项——前提是宿主支持嵌套虚拟化，
且工作负载不依赖被该运行时遗漏的系统调用。

**8.4 一条对交付形态的推论。** 由于硬件虚拟化档被硬件卡住，而加固与隐藏两层的改进都不需要更换
运行时，合理的形态是**分档并存**：默认档在任何有容器引擎的宿主上提供"加固 + 可选的隐藏"，
强隔离档在宿主具备相应能力时才提供。这要求运行时接口本身可插拔——把具体运行时的假设挡在
业务层之外。

## 9 局限

- **单机、单一时段、样本量小**。全部实测在两台机器上完成，其中信息隐藏类实验只有一台真机。
  结论的**方向**可靠（对照测量、命令可复现），但**绝对数值**不应外推。
- **两个论断未能核实**。(a) 一项对比研究中提到的、面向容器 CPU 拓扑隔离的内核提案，
  其项目页面已失效、幻灯片无法解析正文，合并状态未确认；(b) 一篇容器安全综述位于付费墙后，
  本文只读到题录，因此未引用其分类结论。
- **部分依据来自厂商材料**。关于"按名字匹配的执法可被绕开"的批评、以及"限制未特权用户命名空间
  可减少 3.4 倍内核攻击面"的数字，分别来自运行时监控厂商与安全加固站点，本文已注明并打折；
  其中前者有公开 CVE 作为独立佐证。
- **端到端未验证**。应用自身的进程沙箱链是在**探测层**验证的（逐档探测命令），
  未经完整会话验证；一个完整的 agent 任务（含模型调用）在强隔离运行时下未能执行。
- **未覆盖的攻击面**：镜像供应链（签名与来源证明）、运行时检测（本文只讨论其位置，未做选型实测）。

## 10 相关工作

**分层模型与清单。** NIST SP 800-190[2] 给出了五层风险模型，本文的"施加点"判据与之一致，
但补上了工程上更常用的表述（哪些控制住得进安全论证）。容器厂商的运行时加固文档[3] 与各类
CIS 派生清单提供了条目，本文的工作是**逐条实测其效力与失效模式**。

**沙箱与逃逸。** 面向 AI agent 的逃逸基准[1]把威胁模型形式化为"有 shell 权限的对抗性 agent"；
对沙箱引擎的六轴对比[8]给出了架构类与补丁节奏的量化差异；针对配置错误组件的互联网测量[5]
给出了默认配置在真实世界的暴露规模。

**信息泄漏与侧信道。** 页缓存计时侧信道[14]、内核锁争用测量[15]、内核数据结构占用率泄漏[16]
与 CPU 频率指纹[17]分别覆盖了不同的泄漏路径。与本文的关系是互补：它们各自深入某一条路径，
本文的贡献是把**文件系统层的泄漏**与这些机制并列，并给出运行时封装对内核缓解机制的阻断
（7.3）这一工程结论。

**资源可见性。** 用户态 `proc` 覆盖方案[9][10] 的定位是让容器内的 `free`/`top` 显示自己的限额。
本文确认了这一路线的能力边界（八项里三项生效），并指出其结构性上限（`sysinfo(2)` 绕过）。

## 11 结论

把容器当作不可信代码的边界是可行的，但"可行"的准确含义是：**边界等于运行时与宿主施加的控制，
加上一个必须写下来的缺口清单。**

三条具体结论：

1. **按施加点分层**。凡是由工作负载够不到的机制施加的控制（镜像、运行时、宿主）才算边界；
   住在工作负载可写空间里的控制（应用自带沙箱、容器内的校验、容器内的监控与日志）不计入安全论证。
   应用进程沙箱不是平台的边界，它是产品功能。
2. **加固要按真实流程验收，并明确它只是纵深**。加固项的市场失效模式是静默失败；
   seccomp/LSM 应核验实际生效与策略覆盖，不能用进程名检测的缺陷否定内核控制。
   补丁节奏与隔离技术选型都影响风险，不能互相替代。
3. **信息隐藏有结构性上限，但比通常认为的更高**。用户态方案只能降低可读性（八项里三项生效，
   且被 `sysinfo(2)` 绕过）；内核层已经有能覆盖它的机制，卡在运行时不暴露开关；
   而侧信道（页缓存、内核锁、CPU 频率）在任何虚拟化档位下都收不干净。
   因此正确的目标不是"藏干净"，而是**量出真生效的部分、把挡不住的写明**。
