# dshcloud 目标方案：两档部署的多用户工作空间平台

日期：2026-09-19。状态：供评审的目标方案，不表示已实施或已通过生产验收。

本文从业务出发选择方案，不以现有代码为约束。实施步骤见[改造落地文档](PLATFORM-MIGRATION-PLAN.md)，当前完成情况和发布阻塞项见[生产落地状态](PRODUCTION-READINESS.md)。全面实施已开始，但本文描述的目标不等于当前能力，也不自动替代已生效的 ADR；实施时须同步更新现状与决策文档。

## 1. 推荐结论

采用单机 Linux + Docker 的容器平台。同一安装器提供「标准部署」与「加固部署」，共用产品功能、镜像和管理界面，通过版本化策略决定隔离要求。第一版不引入 k3s，不自研内核沙箱，不把 gVisor 或 Kata 作为安装前提。

标准档面向自己、朋友和可信小团队；加固档以工作空间内可能执行敌意代码为设计前提，强制落实运行时、网络、浏览器、资源与运维边界。两档都保留共享内核的剩余风险。加固档可以承载不可信代码，但不是专门的恶意软件分析设施，也不承诺抵御未知内核逃逸或硬件侧信道。

这不是把安全留给高级档：认证、跨工作空间隔离、非 root、禁止提权和硬配额是两档共同底线。加固档的区别是更严格的宿主条件、出网范围、发布准入和持续检查，而不是换一个名称。

若业务最终要求「工作空间失陷后，即使利用宿主 Linux 内核漏洞，也不能影响其他工作空间」，普通 Docker 无法满足。届时在同一平台接入 Kata 等具有独立 guest 内核的容器运行时，并接受 KVM 与资源成本；不能用额外参数代替这项架构变化。

## 2. 必须满足的业务

| 业务要求 | 目标行为 |
|---|---|
| 自部署、低成本 | 一台受支持的 Linux 主机可安装；不要求 Kubernetes、KVM、外部身份系统或监控集群 |
| 邀请制 | 无公开注册；管理员邀请、停用账号、设置配额 |
| 一人多个工作空间 | 每个工作空间独立运行、独立数据、独立授权；同一用户的两个空间也不自动互通 |
| 完整 dsh | 对话、命令执行、Git、语言依赖安装、终端、开发服务器、文件读写可用 |
| 用户可定制 | 用户插件、配置和受支持的 UI 扩展可变且持久；平台不把用户服务当作可信安全组件 |
| 升级不丢内容 | 文件、会话、插件、配置和用户依赖全部在持久数据中；升级失败可恢复旧版本和对应数据 |
| 资源受控 | CPU、内存、进程数、磁盘字节和 inode 有实际限制；日志、临时文件和快照也不能无限增长 |
| 只能经平台访问 | 页面、API、WebSocket、SSE、开发预览都校验用户与工作空间归属 |
| dsh 内部自治 | 模型提供方与用户自己的 key 仍由 dsh 管理；不向工作空间注入平台共享 key |

「完整 dsh」不等于宿主管理员权限。用户在 `/data` 安装 npm/pnpm、Python venv 等依赖；需要系统包时选择管理员发布的镜像配方。配方可以预装编译器、浏览器及其库。禁止给工作空间 Docker socket 或平台代执行任意 root 命令。

上述系统包方式是方案的明确产品取舍，不是已确认的新需求。若必须让每个用户随时执行 `apt install`、嵌套 Docker 或加载内核功能，需要重新评估用户命名空间或更强运行时，不能私自放宽当前档位。

## 4. 两档到底差在哪里

| 项目 | 标准部署 `standard` | 加固部署 `hardened` |
|---|---|---|
| 面向用户 | 自己、朋友、可信小团队 | 受邀但不可信的使用者、可能有敌意的代码 |
| 宿主 | 受支持 Linux，可与其他服务共存 | 专用 Linux 主机，不混放其他业务和凭据；无需第二台主机 |
| 基础隔离 | 非 root、NNP、CapDrop ALL、只读根、独立网络/卷、硬配额 | 相同底线，额外要求经认证版本的 AppArmor/SELinux 策略与持续检查 |
| 网络 | 禁工作空间互访、宿主、内网及元数据；默认允许公网 TCP/UDP | 公网出站默认只允许受控 HTTP(S) 代理及平台 DNS；其他协议按实例显式授权 |
| 内网业务 | 管理员按目的地址/端口授权，默认不开放 | 同样按实例授权并审计；不允许因此打开控制面、节点代理或元数据接口 |
| 浏览器 | 独立子域 + host-only 平台凭据 + 单空间会话 | 同样；另要求控制台与工作空间使用不同注册域 |
| 镜像与更新 | 仅管理员发布的固定 digest；更新提醒 | 校验发布证明、兼容矩阵和策略版本；到期未处理的严重风险阻止新启动 |
| 备份 | 提供备份/恢复能力，管理员决定计划 | 配置外部备份目的地，完成恢复演练才判为生产就绪 |
| 失败处理 | 核心隔离或配额失效一律阻止启动 | 同样；强制项失效还需隔离受影响的现存工作空间 |

独立注册域示例：控制台 `console.team.example`，工作空间 `a.team-workspaces.example.net`。`console.example.com` 与 `a.work.example.com` 仍属于同一注册域，不满足这一额外条件。加固档因此需要额外域名/DNS 配置，这是实际部署成本。

加固档默认代理允许一般公网 HTTPS，以保持模型调用、Git HTTPS、包管理和下载。它阻断直接出站连接、内网探测和未授权协议，不代表阻止公网数据外传；恶意代码仍可能通过允许的 HTTPS 通道外传它本来可读的数据。更严格的域名允许列表是可选策略，启用前必须验收实际依赖源。

## 5. 目标架构

```text
浏览器
  └─ TLS 入口（仅公开 80/443）
       ├─ 控制台域 → Web/API → PostgreSQL
       └─ 工作空间域 → 工作空间访问网关 → 指定工作空间

控制面 → 本机受限 Unix socket → 节点代理（高权限）
                               ├─ Docker 生命周期
                               ├─ 网络策略
                               ├─ 数据池/配额/备份
                               └─ 运行参数与健康事实

工作空间 → 自己的 /data
         → 平台 DNS / 出站规则（加固档经代理）
```

控制面不挂 Docker socket、整个数据池、`/dev`，不持有 `CAP_SYS_ADMIN`。节点代理是明确受信的高权限组件，仅在本机 socket 提供受限操作；这是缩小可直接利用的管理接口，不代表控制面失陷后用户资源仍安全。控制面仍有管理所有工作空间的业务权限。

节点代理只接受实例 ID、已批准镜像 digest、规格和版本化策略；不接受任意宿主路径、shell、挂载、Docker 原始 JSON 或任意镜像。它独立校验资源归属、路径和允许值，不把调用方传来的字符串拼成宿主命令。管理接口不可由工作空间网络访问。

默认仍同机运行控制面与负载，避免强制增加服务器数量。节点宿主被攻陷仍可能危及同机控制面和数据库；进程拆分不是机器级隔离。未来业务提高要求时再分离工作节点。

## 6. 访问认证必须在工作空间外闭环

采用一个受信的工作空间访问网关，负责固定主机名映射、认证、授权、Cookie 隔离和代理。TLS 入口把工作空间域交给它；不再为每条工作空间路由分别手写认证中间件。未知 Host、未知实例、不可用实例默认拒绝。

1. 控制台登录 Cookie 使用 `__Host-` 前缀、Secure、HttpOnly、Path=/、无 Domain；控制台写操作验证精确 Origin 和 CSRF，不只依靠 SameSite。
2. 用户访问工作空间时，网关建立短时登录事务，在该主机种下受保护的事务 Cookie，再跳转控制台授权。
3. 控制台确认当前用户、owner、实例及固定回调地址，签发一次性授权码。授权码绑定事务、实例、用户、原始会话和精确回调，建议有效期 60 秒。
4. 网关验证 state/事务并经受信后端原子兑换授权码，建立仅适用于该实例的随机不透明会话。防重放、登录 CSRF、开放重定向和跨实例兑换。
5. 网关设置自己的 `__Host-` HttpOnly 会话 Cookie；向 dsh 转发前移除所有平台 Cookie 和保留头；响应方向解析并移除工作负载伪造的保留 Cookie。只允许后端 Cookie 无 Domain 或限定当前主机，不能通过父域写入其他站点。
6. 授权回调路径由网关保留，不转发给 dsh；授权码不记日志、不缓存，页面不加载第三方资源，立即跳转干净 URL，并设置 `Referrer-Policy: no-referrer`。
7. 每次请求校验会话有效性及归属，缓存最长建议 30 秒；封禁、注销、撤销会话和删除实例发出撤权事件。网关对已有 WS/SSE 最长 30 秒重新检查并主动断开，不只校验握手。

上述流程沿用成熟的授权码交换思路，协议细节优先使用成熟库，禁止自行设计签名算法。网关故障或授权状态无法确认时拒绝新访问；长连接在撤权检查期限内关闭。具体时限是设计目标，需实测达标。

工作负载可以修改自己的 dsh/Caddy，但不能绕开网关访问其他实例。内部桥签名可以继续作为纵深措施，不能成为唯一外部边界。开发预览若纳入产品，同样经网关授权；不开放匿名端口或改成控制台同源路径。不同预览应用应使用不同 origin。

## 7. 容器、镜像与可定制性

两档共同使用：固定非 root uid、`no-new-privileges`、`CapDrop: ALL`、独立 PID/mount/network/IPC namespace、只读 rootfs。保持受认证 Docker 版本的默认 seccomp，不使用 unconfined，不开启 privileged/host PID/host network，不挂宿主设备和 runtime socket。

`/data` 是唯一持久可写区域。`/tmp`、`/run`、`/dev/shm` 使用有上限的临时存储，纳入内存预算；需要执行编译产物的目录不能盲目 noexec。基础镜像预装常用系统依赖；可执行入口及平台适配文件使用绝对路径，不从用户可改的 PATH 加载高权限程序。

只读根不禁止用户定制。标准插件、配置、语言环境和受支持 UI patch 保存在 `/data`。直接修改系统镜像文件不作为持久定制方式；管理员可发布派生镜像。镜像配方属于受信管理员能力，不能允许普通用户把任意 Dockerfile 交给有宿主权限的构建器执行。

加固档强制启用适配 dsh 的 AppArmor 或 SELinux 策略。策略在宿主施加，禁止挂载、宿主设备、内核管理等不需要的能力；文件写入范围与业务一致。不声称维护一份更长的 syscall 黑名单就获得绝对安全。

seccomp 实际按系统调用及可检查参数过滤，并不按命令名称过滤；改文件名、换 shell 不能直接绕过。AppArmor/SELinux 也是内核强制机制。旧文档关于「改二进制名称即可绕过 seccomp」的说法不能作为本方案依据。[S10]

## 8. 网络策略

每实例独立网络；禁止实例之间直接通信。入口到后端是唯一入站路径。无论目的地址是私网还是公网，都拒绝实例主动连接宿主自身地址、控制面、数据库、节点代理和其他实例。

网络控制在宿主实施，分别覆盖宿主 INPUT 与路由 FORWARD；显式处理 Docker DNAT 后的地址、hairpin、宿主公网地址、IPv6、链路本地地址和云元数据。要么完整支持 IPv6 并测试，要么在工作空间网络明确禁用，不能只写 IPv4 规则。

规则只作用于平台登记的桥和资源，不使用 `br-*` 一刀切影响其他容器。策略必须在工作空间开始执行代码前存在；网络/Docker/防火墙重启后检查和恢复。网络创建、规则应用、容器启动作为同一个可恢复操作。

加固档禁止绕过代理直连公网，代理每次连接和重定向都检查实际目标 IP，阻断私网、特殊地址、元数据及宿主地址，抵御 DNS rebinding。HTTP CONNECT 不允许任意端口。平台 DNS 与代理应有按实例限流；只做「解析域名后允许 IP」不等于可靠域名策略。

代理客户端变量是便利设置，不是安全边界，宿主规则才是。Git SSH、非 HTTP 模型接口等通过管理员显式按实例授权；页面说明具体受限能力。标准档允许配置私有模型服务的例外，但不允许宽泛放开整个内网。

## 9. 存储和资源

使用宿主 XFS project quota，按不可复用 storage ID 分配独立目录和 project ID，字节与 inode 双限。有原生 XFS 则直接使用；否则允许预置 loopback XFS，但检查宿主实际可用空间、挂载持久性和水位，不能把稀疏文件的名义容量当成真实容量。

CPU、内存、swap、pids、nofile 均设置上限。容器日志轮转并设总量上限；镜像缓存、快照、备份暂存另设平台预算。保留控制面和宿主的资源余量，限制并发拉镜像、启动、升级和备份。加固档还需限制出站带宽/连接速率，并在认证环境测试磁盘 I/O 限制。无法提供的隔离维度必须如实列明，不能把 CPU/内存限额等同于全资源公平。

数据满只影响该实例；池接近满时阻止创建和升级，已有服务保持可读与可恢复。缩容低于实际用量时拒绝新写而不删旧数据。数据卷缺失、配额设置或读回失败必须报错，不能创建空目录假装恢复成功。

升级步骤：拉取并校验镜像 → 校验额外容量 → 暂停入口并优雅停机 → 一致性快照 → 新版本健康与最小业务检查 → 恢复入口。失败恢复旧镜像和旧数据；开放写入后的手动数据回滚需明确提示会丢失快照后的修改。

快照不是灾备。备份包括逐实例数据、平台数据库、镜像/策略版本和恢复所需密钥；目的地凭据只在受信服务中。恢复必须保留实例归属，不能通过重用 slug 关联到旧数据。加固档要求有外部副本，且实际完成单实例与整机恢复演练。

## 10. 安装、升级和运行保障

同一个安装器提供以下拟议接口（尚未实现）：

```sh
bash install.sh --profile standard
bash install.sh --profile hardened
bash install.sh profile set hardened
bash install.sh doctor
```

两档都不使用弱安全默认。加固档增加专用宿主、域名、LSM、网络代理、备份和认证版本检查；不满足就给出具体缺项，不静默退回标准档。不自动改动宿主已有 Docker 的 userns/rootless 配置或重启其他业务。

部署身份、所需策略、已应用策略和检查结果分开记录。安装成功只表示服务装好；通过业务、攻击、重启与恢复验收后才表示生产就绪。macOS Docker Desktop 只支持开发，不可认证成加固生产档。

切换档位是迁移：预检 → 备份 → 按实例停机重建 → 实测 → 标记生效。迁移期间逐实例展示实际状态；所有实例达标前不能显示整个平台已加固。降档必须显式操作并审计，更新失败不能隐式降档。

操作持久化到 PostgreSQL，带实例级锁、幂等键和操作阶段。进程崩溃后可继续或回滚；同步 HTTP 请求不承担整个升级事务。第一版使用数据库任务表即可，不要求 Redis。

外部观测以节点代理的资源事实、入口日志和平台审计为准。最小告警覆盖磁盘水位、备份失败、策略漂移、重复崩溃、异常资源与撤权失败；不把容器自身的日志视为不可伪造证据。先提供可用告警出口，再考虑 Falco 等附加检测。

内核、Docker/runc/containerd、基础镜像、网关与认证库都进入更新清单。建议已知可利用的严重逃逸风险发现后 24 小时内评估并采取阻断/停用措施，72 小时内完成可用修复或明确停用受影响档位；这是待团队确认的运营目标，不是现有承诺。签名验证证明来源，不证明镜像无漏洞。

### 10.1 已有服务的 Linux：两档支持范围

「不是全新系统」不等于不能安装。判断依据是宿主是否受支持、是否受信、是否有资源和配置冲突，而不是安装日期。预检只能发现可观测配置，不能证明系统没有被入侵。已失陷或来源不明的宿主应重新建立可信环境，安装加固档不能清除宿主恶意程序。

| 宿主情况 | 标准档 | 加固档 |
|---|---|---|
| 已装 Docker，没有其他业务 | 版本与配置通过检查即可 | 专用用途且其余强制项通过即可，不要求重装 |
| 已运行网站、数据库或其他容器 | 支持受限共存，先检查入口、网络、容量和权限 | 不支持作为加固生产部署；应先迁走其他业务或使用专用 VM/主机 |
| 有受支持的监控、日志、备份、安全管理软件 | 检查规则与资源影响后允许 | 可以存在；专用宿主不等于只能运行平台进程 |
| 已有 k3s、复杂 VPN、未知防火墙组合 | 不自动接管；没有验收过的组合阻止安装并列出冲突 | 同样拒绝未经认证组合，不通过关闭保护强行安装 |
| 与不可信用户共享宿主 root/Docker 管理权限 | 无法提供对这些宿主管理员的隔离保证 | 不满足受信宿主条件 |

专用 VM 是可选部署位置，不要求给每个工作空间再套 VM；其中仍运行本方案的 Docker。若用户只愿意在混有其他业务的同一 Linux 系统上部署，应选择标准档，不能仅凭开启几个保护项标为加固档。

### 10.2 共存可能造成的影响与处理

| 冲突面 | 可能影响 | 安装器的目标行为 |
|---|---|---|
| 80/443 与已有反向代理 | 抢占网站入口，或证书验证失败 | 不停止已有服务；支持独占入口或接入现有入口两种模式，冲突未解决前不安装 |
| Docker 版本与全局配置 | 升级/restart、改 userns/地址池影响所有容器 | 复用受支持配置；不自动升级、重启已有 daemon，不覆盖 daemon.json；不兼容时退出 |
| 防火墙、VPN、网段 | 误断其他容器、SSH、VPN；旧规则绕过隔离 | 只操作登记的本平台规则/接口，检测网段与规则管理器；未知组合拒绝，无全表清空 |
| 存储池与已有数据 | 格式化误伤、loopback 占满宿主盘、fstab 冲突 | 不格式化已有设备、不复用非空未知目录；显式分配平台预算，只添加可归属的挂载项 |
| CPU/内存/磁盘 I/O/网络 | 现有网站变慢、OOM、备份和拉镜像抢资源 | 设置平台总预算及并发上限，留现有业务余量；不能承诺共享硬件完全无干扰 |
| sysctl、LSM、内核更新 | 全机网络语义或安全策略变化，重启其他业务 | 不静默改全局开关、不关闭 SELinux/AppArmor；需要全局操作时停止自动流程并输出具体维护步骤 |
| 卸载与失败回退 | 误删共享镜像/卷、撤掉他人规则 | 按安装资源清单处理；禁止 system prune、全局卸 Docker 或无差别恢复旧防火墙快照 |

标准档混部会扩大故障影响：本平台负载耗尽共享资源会影响其他服务，其他服务占满磁盘或重启 Docker 也会影响工作空间。其他服务若取得宿主 root 或 Docker socket，则可以读取/修改本平台资源；这一风险不能靠平台内部认证消除。

反方向也成立：工作空间中的代码一旦通过共享内核漏洞逃逸，宿主上原有网站、数据库和凭据也可能受影响。普通版的混部支持只表示特定组合经过兼容性验收，不表示这些业务具有独立的安全边界。因此不建议把需要保护的重要数据库或生产密钥与不可信代码放在同一宿主系统中。

若只有一台物理服务器且已有业务，可以为平台分配一台专用 Linux VM，再在其中运行 Docker；这不是每个工作空间一台 VM。它将平台与原有业务分到不同 guest 内核，但仍共享物理资源、虚拟化层和管理权限，不能消除资源争用或防御不可信的虚拟化管理员。标准档升级到加固档时，混部主机须先完成这一部署调整或迁走其他业务，不能只执行加固命令就宣告达标。

### 10.3 已有入口接入与安装变更清单

独占入口模式由平台负责 TLS 和 80/443。已有入口模式由管理员在现有 Nginx/Caddy/Traefik 配置控制台及工作空间域名转发，平台只监听指定回环端口；平台不自动编辑已有站点或签发冲突证书。TLS、证书续期和域名挑战由已有入口负责。

已有入口必须保留实际 Host，支持 WebSocket/SSE 和合适超时，不缓存认证回调及私有响应；访问网关仍负责最终认证和授权，不能将其绕过直连工作空间。转发头只信任固定上游。既有入口若在容器中，不能假设其能访问宿主回环；第一版只支持经过验证的宿主入口或明确的专用入口连接网络，否则给出不支持原因。

安装增加只读 `preflight` 和 `--dry-run`（均为拟议能力）：先报告端口占用、Docker/网络配置、磁盘容量、将创建的服务/目录/挂载/规则和接入模式。预检不拉镜像、不安装包、不写防火墙或 fstab。依赖变更、存储容量和入口方案未确定前不进行写入；干净主机可使用公开且有界的默认值，共存主机要求显式平台资源预算，不默认占用剩余磁盘的 80%。

写入阶段记录每项新建资源及归属，尽量先完成下载与校验再切换入口。安装失败只撤回本次拥有且未被其他操作修改的资源；数据不自动删除。安装、升级和卸载均显示影响清单，重跑前重新检查，不能用安装时的一次快照保证永久共存。

## 11. 方案准入与不做的事

两档必须通过同一套 dsh 业务验收；加固档再叠加恶意代码和部署故障测试。不能为了通过安全测试关掉命令执行、插件安装或持久化，也不能为了业务通过取消宿主强制保护。

必须实测：命令沙箱、终端、npm/pnpm、Python venv、Git HTTPS、模型流式响应、编译产物、浏览器工具（如纳入支持范围）、开发服务、插件真实渲染、升级与回滚。具体镜像/内核/运行时/LSM 组合通过后才加入兼容矩阵。

gVisor 暂不进入目标默认实现：本仓库已有当前 dsh 沙箱链不兼容的记录，不能只因它安全性更强就认为业务可用。未来版本可以重测，不能偷偷关闭 dsh 的安全功能来宣称兼容。

不采用 k3s 的原因是当前需求为单机、自部署、小团队；换编排器不改变共享内核边界，反而增加维护面。出现多机调度、高可用或已有 Kubernetes 运维条件时，再参考 Che 增加执行器。

平台不保护工作空间中的数据免受该工作空间自己的代码破坏或读取，也不保证用户填入 dsh 的 key 对同空间恶意代码保密。用户把秘密交给能读它的执行环境，不能靠跨实例隔离解决。
